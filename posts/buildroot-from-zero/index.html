从零构建嵌入式 Linux：Buildroot
yanruiheBuildroot
2026-09-23 · Buildroot 2025.02.18 LTS · QEMU x86_64

从源码生成交叉工具链、Linux 内核和根文件系统，在 QEMU 中启动并验证，而不是只编译一个程序。QEMU 的虚拟 BIOS 负责早期引导；真实 ARM 板仍需对应 Bootloader、设备树和 BSP。

构建原理 · 主机准备 · 构建 · 启动 · 配置迭代 · 排错 · 产品交付

先弄清原理：Buildroot 为什么能构建一整套系统？

Buildroot 不是用 C 语言重新实现 Linux。它本身主要由 Makefile、Kconfig 配置、脚本和补丁组成；内核、GCC、C 库、BusyBox 等来自各自独立的上游项目。Buildroot 负责选择版本与选项、处理包之间的依赖、下载源码、交叉编译、安装到目标根文件系统，再生成指定格式的镜像。因此，make 触发的是一条受配置驱动的构建链，而不是编译一个巨大的 C 项目。

板级 defconfig → .config → 工具链（binutils / GCC / C 库，或外部工具链）
                          → 目标软件（例如 BusyBox 和自己的应用）
                          → 内核 / 可选 Bootloader → 根文件系统 → 镜像

这是一张职责图，不是严格的任务执行顺序；具体组件取决于配置。本文的 qemu_x86_64_defconfig 生成内核和根文件系统，QEMU 使用虚拟 BIOS，没有在这个示例中构建 U-Boot。C 库也不是固定为 musl，可按配置选择 glibc、musl 或 uClibc-ng 等。BusyBox 提供精简用户空间工具和默认 init；它不是内核，也不是 Buildroot 本身。

1. 准备构建主机

在 Linux 主机上以普通用户构建。Windows 可用 Linux 虚拟机或 WSL2 的 Linux 文件系统；不要把大型构建目录放在 Windows 挂载盘。下面以 Ubuntu 24.04 为例，其他发行版参考官方主机依赖。预留足够磁盘、内存和网络带宽。

sudo apt update
sudo apt install -y build-essential git wget cpio unzip rsync file bc \
  bzip2 gzip xz-utils patch sed gawk qemu-system-x86

仅安装主机依赖需要 sudo；不要使用 sudo make。

2. 固定版本并构建完整镜像

git clone --branch 2025.02.18 --depth 1 https://gitlab.com/buildroot.org/buildroot.git buildroot
cd buildroot
git describe --tags --always
make qemu_x86_64_defconfig
make
ls -lh output/images/
test -s output/images/bzImage
test -s output/images/rootfs.ext2

首次构建会下载源码并生成工具链、目标软件、内核与根文件系统；不要盲目给顶层 make 加 -j。读懂产物目录，排错和发布才不会混淆：

路径用途
.config本次构建的完整选择；用 make savedefconfig 提炼为便于版本管理的板级配置
output/build/各组件的解包、配置和编译现场
output/host/主机工具、交叉工具链和目标 sysroot；output/staging/ 是指向 sysroot 的兼容性链接
output/target/接近目标根文件系统的安装树，但缺少正确设备节点和部分权限，不能直接部署
output/images/内核、根文件系统及当前配置所选择的其他最终产物

3. 启动 QEMU 并验证

使用所选 defconfig 的板级说明中的启动参数：

qemu-system-x86_64 -M pc \
  -kernel output/images/bzImage \
  -drive file=output/images/rootfs.ext2,if=virtio,format=raw \
  -append 'rootwait root=/dev/vda console=tty1 console=ttyS0' \
  -serial stdio -net nic,model=virtio -net user

登录提示默认出现在 QEMU 图形窗口。进入客户机后检查：

uname -a
cat /proc/cmdline
cat /proc/1/comm
mount | grep ' on / '

确认内核、根设备、init 和根文件系统后，从客户机运行 poweroff。不要直接修改 rootfs.ext2 充当持久配置。

4. 加一个开机动作

这个最小配置使用 BusyBox init，不是 systemd。先执行 mkdir -p board/demo/overlay/etc/init.d，再创建 board/demo/overlay/etc/init.d/S99demo：

#!/bin/sh
case "$1" in
  start) echo 'Buildroot demo is ready' >/dev/console ;;
  stop) ;;
  *) exit 1 ;;
esac

运行 chmod +x board/demo/overlay/etc/init.d/S99demo，再执行 make menuconfig；在 System configuration → Root filesystem overlay directories 填入 board/demo/overlay。保存后再次 make、启动 QEMU。启动日志应出现提示，客户机中可用 test -x /etc/init.d/S99demo 检查。正式应用应做成 package，overlay 仅用于最小演示。

5. 固化配置并迁移到真实硬件

make savedefconfig BR2_DEFCONFIG=board/demo/demo_defconfig
git status --short

提交 defconfig、overlay、补丁与版本清单，不提交整个 output/。只有配置文件还不足以保证逐字节复现：还要固定 Buildroot 与外部源码版本、补丁、工具链及构建环境。真实开发板需对应的 board defconfig，并逐项核对 CPU/ABI、Bootloader、内核配置、设备树、分区、串口和刷机方法；QEMU 镜像不能直接刷进不相干的硬件。构建失败查看失败包及 output/build/；启动失败先检查内核命令行、根设备和串口。Buildroot 也不会自动解决 OTA、安全更新和产品生命周期管理；发布前处理软件许可证及源代码提供义务。若项目需要多层元数据和发行版策略，可对照Yocto 从零构建篇选择方案。

6. 从配置到镜像：逐层理解构建

Buildroot 的菜单是在描述目标产品需要哪些组件。make qemu_x86_64_defconfig 把维护过的默认选择写进 .config；make menuconfig 修改选项；顶层 Makefile 按软件包依赖安排任务。工具链提供目标编译器、链接器和 C 库，用户空间程序使用这套工具链；内核与 Bootloader 分别从各自上游源码构建。

例如，选中一个依赖 OpenSSL 的网络程序时，依赖图会先准备目标头文件和库，再交叉编译该程序。每个包的 .mk 说明源码地址、配置、编译和安装方式；Config.in 决定菜单选项。根文件系统 skeleton、包、overlay、设备表与权限共同形成用户空间，文件系统生成器最后打包成所选格式。这就是 Makefile 驱动的集成工程能够构建完整系统的原因：Buildroot 组织构建，组件仍是独立项目。

阶段主要输入结果
配置defconfig、menuconfig、板级选项.config、内核与 BusyBox 配置
工具链CPU/ABI、C 库、编译器版本output/host/bin/ 下的交叉工具
系统组件内核、可选 Bootloader、BusyBox、软件包安装至 staging/target 的文件
镜像生成skeleton、overlay、设备表、文件系统类型output/images/ 中的启动/烧录产物

Buildroot 可构建内部工具链，也可接外部交叉工具链；C 库按目标选择。QEMU 示例由虚拟固件加载内核，适合验证内核与用户空间协作。真实板通常还要准备 Bootloader、DDR/启动介质初始化、设备树及厂商 BSP，应提前划分 Buildroot 与厂商 BSP 各自负责的部分。

7. 配置修改与小步迭代

mkdir -p board/demo
cp .config board/demo/qemu_x86_64_base.config
make menuconfig
diff -u board/demo/qemu_x86_64_base.config .config
make
make savedefconfig BR2_DEFCONFIG=board/demo/demo_defconfig
diff -u configs/qemu_x86_64_defconfig board/demo/demo_defconfig

常用菜单包括 Target options（架构/ABI）、Toolchain（C 库/编译器）、System configuration（hostname、密码策略、init 和设备管理）、Target packages、Kernel 与 Filesystem images。每增加一个软件包都会增加镜像、依赖、维护和安全工作，应从板卡与应用需求出发选择。

Linux、BusyBox 和 C 库有各自的配置器，不是 Buildroot 包菜单本身：

make linux-menuconfig
make busybox-menuconfig
make uclibc-menuconfig   # 仅当配置使用 uClibc-ng

内核配置可用 make linux-update-defconfig 保存；BusyBox 有 busybox-update-config。可用目标依配置而异，先查 make help 和固定版本的手册。将精简 defconfig、内核/BusyBox 配置、补丁和 overlay 一起纳入版本控制，不要提交含本机绝对路径的单份 .config。修改包后可先单独重建：

make openssl-show-depends
make openssl-rebuild
make V=1

把示例中的包名换成实际 target。V=1 显示完整编译命令，便于检查参数、头文件和链接库；若改了配置或依赖，单独 rebuild 可能不够，按需使用该包的 reconfigure/dirclean，再由顶层 make 更新依赖。

8. 添加文件、应用与服务

Root filesystem overlay 适合少量默认配置、静态文件和启动脚本；overlay 的目录层级对应目标根目录，board/demo/overlay/etc/... 会出现在客户机的 /etc/...。本文的 S99demo 使用 BusyBox init。Buildroot 的 init 可配置；若选 systemd，应使用 systemd unit 和相应包配置，不能把 BusyBox /etc/init.d/ 脚本当成通用服务定义。

overlay 不能替代软件包。正式应用应做成 Buildroot package，让源码版本、依赖、编译参数、安装路径与许可证信息可审查和重建。自定义 package 通常由 Config.in 与 .mk 组成：前者定义 Kconfig 选项与依赖，后者描述源码获取、交叉编译和安装。将它们放进 BR2_EXTERNAL 外部树并与产品 defconfig 一起版本管理，避免直接修改 Buildroot 上游树。需要多发行版和更多元数据复用时，继续看Yocto 从零构建篇。

9. 分开排查构建与启动问题

现象先检查下一步
下载失败output/build/<package>/、dl/、错误末尾检查网络/代理、上游地址和校验值，区分下载与编译错误
缺头文件或库失败包的 config.log、依赖菜单确认依赖已选中且没有混淆 host/target 包
链接到主机架构编译命令、output/host/bin/目标包必须使用 Buildroot 的交叉工具链
QEMU 找不到根文件系统启动参数、实际文件名、/proc/cmdline核对 virtio 根设备和实际生成的格式
内核启动但无登录提示console=、getty、QEMU 串口/窗口使用当前 defconfig 对应的板级说明
overlay 文件未进镜像.config 中的路径、文件权限保存 overlay 配置并确认启动脚本可执行

日志通常能指出真正失败的软件包。修复依赖、工具链选择或补丁后重建受影响的包；只有确认输出状态损坏才全量清理。网络受限时可先运行 make source 获取当前配置需要的源码，再将下载目录带到构建机。

10. 从 QEMU 演示走向产品

QEMU 只验证配置能否启动，不验证真实板卡的 DDR、启动介质、GPIO、显示、无线、电源管理和量产刷写。先获取厂商 BSP 与版本支持范围，逐项确认 SoC/ABI、启动阶段、内核 defconfig、设备树、根分区、分区表、串口和升级/回滚策略；先启动最小镜像，再分批加入驱动和应用并保存镜像与串口日志。

make legal-info

审阅 output/legal-info/README 中的警告、组件清单和许可证文本。它只是合规审查的辅助材料。版本库至少保存固定 Buildroot 版本、defconfig、外部树、补丁、板级文件、应用版本和构建说明；CI 应在干净 Linux 主机上重建并保存产物哈希。现场升级还需独立设计签名验证、A/B 或恢复分区、回滚、密钥管理和安全更新策略。
