从零构建嵌入式 Linux：Yocto
yanruiheYocto
2026-09-23 · Yocto Project 6.0.2 · QEMU x86_64

从 6.0.2 源码构建、启动完整的 qemux86-64 镜像，再把 systemd 服务纳入镜像。QEMU 验证内核、根文件系统、init 与应用流程；真实开发板仍需 BSP、Bootloader、设备树和外设适配。

心智模型 · 主机准备 · 获取源码 · 最小镜像 · 服务镜像 · 任务与排错 · 团队交付

先建立心智模型：Yocto 由什么组成？

Yocto Project 不是安装到目标机上的 Linux 发行版，而是一组构建嵌入式 Linux 的项目和规范。Poky 是参考发行版与集成层；OpenEmbedded-Core 提供基础配方和类；BitBake 读取元数据并安排任务。产品构建通常还会加入板级 BSP layer、产品 distro layer、应用 layer 和 image recipe。

MACHINE（硬件） + DISTRO（发行版策略） + IMAGE recipe（产品内容）
                         ↓
              layers 中的 .conf / .bb / .bbappend
                         ↓ BitBake 解析依赖与任务
       fetch → unpack → patch → configure → compile → install → package → image
                         ↓
       tmp/deploy/images/<machine>/ 下的启动与根文件系统产物

Recipe 描述一个软件如何获取源码、打补丁、配置、编译、安装和打包；layer 是这些 recipe、配置与补丁的版本化边界；image recipe 决定最终文件系统包含哪些二进制包。BitBake 将元数据展开为任务依赖图，并用签名与共享状态缓存跳过未变化的任务。系统因此由硬件、发行版策略和软件包集合共同定义，而不是手工复制文件拼成。

名称回答的问题本教程取值
MACHINE目标硬件、CPU、内核和启动配置是什么？qemux86-64
DISTRO使用什么发行版策略、init 和全局设置？poky 参考发行版
Image最终根文件系统安装哪些软件？core-image-minimal / demo-image
Layer哪些配置、配方与补丁属于一个团队/产品？meta-yocto / meta-demo

1. 主机准备与资源

选择官方支持的 Linux 主机。6.0.2 的 core-image-sato 参考配置约需 140 GB 空闲磁盘和 32 GB 内存；本篇最小镜像通常更轻，但仍需充足空间。WSL2 可用但未经官方构建主机验证。Ubuntu 24.04 安装：

sudo apt update
sudo apt install -y build-essential chrpath cpio debianutils diffstat file \
  gawk gcc git iputils-ping libacl1 libcrypt-dev locales python3 \
  python3-git python3-jinja2 python3-pexpect python3-pip \
  python3-subunit socat texinfo unzip wget xz-utils zstd
locale -a | grep -i en_US.utf8

若最后一行无结果，先按官方要求启用 en_US.UTF-8。以普通用户构建，不使用 sudo bitbake。

2. 固定 6.0.2 元数据

按官方手动配置把三个仓库固定到同一发行版：

mkdir -p embedded-yocto/layers
cd embedded-yocto
git clone -b yocto-6.0.2 https://git.openembedded.org/bitbake layers/bitbake
git clone -b yocto-6.0.2 https://git.openembedded.org/openembedded-core layers/openembedded-core
git clone -b yocto-6.0.2 https://git.yoctoproject.org/meta-yocto layers/meta-yocto
source layers/openembedded-core/oe-init-build-env
printf '\nINIT_MANAGER = "systemd"\n' >> conf/local.conf
bitbake-getvar MACHINE
bitbake-getvar DISTRO
bitbake-getvar INIT_MANAGER
bitbake-layers show-layers

脚本会进入 build/。确认 MACHINE=qemux86-64。Yocto 6.0.2 的 nodistro 默认使用 systemd；Poky 参考发行版可能选择不同的 init。本文使用 Poky，因此显式在 conf/local.conf 设置 INIT_MANAGER = "systemd"，并用 bitbake-getvar INIT_MANAGER 确认。正式产品应将选择写入自己的 distro 配置，而非依赖开发者个人的 local.conf。

3. 构建和启动最小镜像

bitbake core-image-minimal
ls -lh tmp/deploy/images/qemux86-64/
runqemu qemux86-64 core-image-minimal ext4 nographic

若未生成 ext4，先查 bitbake-getvar IMAGE_FSTYPES 并选实际类型。首次编译会下载许多依赖；不要提交 tmp/、downloads/ 或 sstate-cache/。客户机内验证：

uname -a
cat /proc/cmdline
cat /proc/1/comm
mount | grep ' on / '

登录策略依镜像配置而定。仅限隔离的 QEMU 演练镜像，可用 EXTRA_IMAGE_FEATURES = "empty-root-password" 允许本地控制台空密码登录；绝不可用于联网或生产镜像，也不要启用 SSH 空密码登录。客户机运行 poweroff 后再继续。

4. 加入并启动 systemd 服务

仓库的meta-demo 示例层包含脚本、unit、Recipe 和 demo-image。从 embedded-yocto/build/ 回到源码根目录；先用 pwd 核对：

cd ..
git clone --depth 1 https://github.com/yanruihe/yanruihe.github.io.git site
cp -a site/knowledge-base/examples/meta-demo layers/meta-demo
source layers/openembedded-core/oe-init-build-env
bitbake-layers add-layer ../layers/meta-demo
bitbake-layers show-recipes hello-yocto
bitbake demo-image
runqemu qemux86-64 demo-image ext4 nographic

进入客户机：

cat /proc/1/comm
systemctl is-enabled hello-yocto.service
systemctl is-active hello-yocto.service
cat /run/hello-yocto/status
journalctl -u hello-yocto.service -b --no-pager

应看到 enabled 与 active；否则检查 init、包是否入镜像、unit 路径和日志。示例镜像带 Dropbear，仅适用于隔离开发；部署前关闭不需要的 SSH 并设置合理的账户与密钥。示例 Recipe 的 LICENSE = "CLOSED" 只是演示占位。

5. 迁移真实开发板

记录仓库 commit、MACHINE、DISTRO、INIT_MANAGER、各层修订与镜像产物。选择兼容 6.0.2 的 BSP，逐项验证 Bootloader、内核配置、设备树、分区、串口、网络、刷机和回滚。功能修改应提交 layer、recipe、config，而非直接编辑 tmp/work/ 或镜像。构建失败看 temp/log.do_*，运行失败看串口、systemctl status 和 journalctl。

6. 看懂 BitBake 任务与构建目录

bitbake core-image-minimal 的参数是 recipe 目标，不是 Linux 内核的 make 目标。BitBake 解析 layer 与配置，计算任务依赖。软件包常见任务包括 do_fetch、do_unpack、do_patch、do_configure、do_compile、do_install 和 do_package。任务可并行，未变化的任务可复用 sstate-cache；所以首次构建慢，后续小改动通常只重建受影响任务。

路径用途是否提交产品 Git
conf/local.conf、conf/bblayers.conf本机目标设置与启用的 layer通常不提交个人 build 目录；产品默认值搬进受版本管理的 layer/distro
tmp/work/recipe 工作目录、编译现场和任务日志否，可重建
tmp/deploy/images/<machine>/内核、bootloader、镜像和 manifest 等产物归档为构建结果，不当源代码
downloads/上游源码下载缓存可共享或缓存，一般不提交 Git
sstate-cache/可复用的任务输出缓存可放团队缓存，不是产品源代码
layers/recipe、配置、补丁及 layer 元数据是；固定各仓库 revision

用 bitbake-getvar MACHINE 或 bitbake-getvar IMAGE_FSTYPES 查询变量最终值；用 bitbake -e hello-yocto 查 recipe 合并后的设置。检查 recipe、layer 与任务：

bitbake-layers show-layers
bitbake-layers show-recipes hello-yocto
bitbake -c listtasks hello-yocto
bitbake -g demo-image

bitbake -g 会生成依赖图文件，可解释某个镜像为什么引入特定软件包。改完 recipe 先构建 bitbake hello-yocto，确认后再构建 bitbake demo-image。不要一遇到错误就删除整个 tmp/；先读 BitBake 报告的失败任务日志和展开变量。

7. 从空目录创建自己的 Layer 和 Recipe

前面的 meta-demo 是仓库提供的完整演示。如果要从头练习，而不是使用该现成层，可创建独立的 meta-practice；不要同时启用包含同名配方的两份演示层：

bitbake-layers create-layer ../layers/meta-practice
bitbake-layers add-layer ../layers/meta-practice
bitbake-layers show-layers

典型结构如下：

layers/meta-practice/
├── conf/layer.conf
├── recipes-demo/hello-yocto/hello-yocto_1.0.bb
├── recipes-demo/hello-yocto/files/hello-yocto.sh
├── recipes-demo/hello-yocto/files/hello-yocto.service
└── recipes-core/images/demo-image.bb

Recipe 继承 systemd class，声明本地文件、安装脚本与 unit，并设置 SYSTEMD_SERVICE:${PN}；image recipe 通过 IMAGE_INSTALL:append 将包加入镜像。示例服务周期性写入 /run/hello-yocto/status，unit 使用 Restart=on-failure；在 QEMU 中用 systemctl 和 journalctl 验证。完整 recipe、安装规则和 image recipe 在meta-demo 示例目录。发布产品时将示例的 LICENSE = "CLOSED" 占位符替换成真实 SPDX 许可证与校验信息。

了解清理的缓存影响：-c clean 清工作目录；-c cleansstate 还会删除该配方的共享状态缓存，让其他构建也失去复用。只有确认缓存导致问题且接受重建成本时才用后者。团队应把 MACHINE、DISTRO、init 和应用选项写入自有 layer；用 bitbake-layers create-layers-setup 或团队的 manifest 工具记录所有 layer 仓库及 revision。

8. 常见故障与定位顺序

现象先检查建议动作
do_fetch 失败代理、DNS、URL、Git branch/tag 和校验确认源码可访问，不要改用未固定的 master
Nothing PROVIDESlayer 是否加入、recipe 名、show-recipes检查 bblayers 与 layer 依赖，区分 recipe/package/image 名
PID 1 不是 systemdbitbake-getvar INIT_MANAGER、发行版配置构建前固定 init，确认使用了预期 build 目录和 distro
服务未启动包是否进镜像、unit 路径、SYSTEMD_SERVICE查 systemctl status 和 journalctl -u ... -b
QEMU 无法启动镜像MACHINE、镜像类型、runqemu 参数核对 deploy 目录实际文件与 IMAGE_FSTYPES
recipe 改动没生效命中的 layer/append、变量展开、任务日志用 bitbake-layers show-appends、bitbake -e hello-yocto 再定向重跑

tmp/work/<arch>/<recipe>/<version>/temp/ 一般有 log.do_* 和 run.do_*：前者记输出，后者是任务执行脚本。先定位 BitBake 报告的失败任务；若服务启动但行为异常，再检查日志、权限、运行时依赖和网络。

9. 团队构建、发布与方案选择

每次可交付构建记录 BitBake、OpenEmbedded-Core、meta-yocto、BSP 和产品 layer 的 revision，以及 MACHINE、DISTRO、INIT_MANAGER、image 目标、源码镜像/哈希服务设置和产物哈希。Review 检查固定 SRCREV/校验值、补丁来源、许可证、运行时依赖和服务权限。local.conf 用于本机试验；产品默认值应在版本化的 distro、machine、image 与 layer 配置中，保证干净 CI 主机可复现。

Buildroot 常适合配置集中、由一个团队产出完整根文件系统镜像的项目；Yocto 常适合多板型、多发行版策略、多个团队共享 layer，以及长期维护 recipe 与 SDK 的产品。还要考虑芯片厂商 BSP、团队经验、更新方案和支持周期。两者都不会自动提供安全 OTA、签名密钥管理或量产回滚设计。
