Yocto build components: Poky, layers, recipes, and BitBake

The Yocto Project is not a Linux distribution installed on the target. It is a set of projects and conventions for building embedded Linux. Poky is the reference distribution and integration layer; OpenEmbedded-Core supplies core recipes and classes; BitBake reads metadata and schedules tasks. Product builds usually add a board BSP layer, a product distro layer, application layers, and an image recipe.

MACHINE (hardware) + DISTRO (distribution policy) + IMAGE recipe (product content)
                                  ↓
                   .conf / .bb / .bbappend in layers
                                  ↓ BitBake resolves dependencies and tasks
     fetch → unpack → patch → configure → compile → install → package → image
                                  ↓
              boot and rootfs artifacts under tmp/deploy/images/<machine>/

A recipe describes how to fetch, patch, configure, compile, install, and package software. A layer is a versioned boundary for recipes, configuration, and patches. An image recipe decides which binary packages end up in the filesystem. BitBake expands metadata into a task dependency graph and uses signatures and shared state to skip unchanged work. The result is defined by hardware, distro policy, and a software set, rather than a root directory assembled by hand.

1. Host prerequisites

Use an officially supported Linux host. The 6.0.2 core-image-sato reference lists about 140 GB free disk and 32 GB RAM; our minimal image is usually lighter but still needs ample resources. WSL2 can work but is not validated as an official build host. For Ubuntu 24.04:

sudo apt update
sudo apt install -y build-essential chrpath cpio debianutils diffstat file \
  gawk gcc git iputils-ping libacl1 libcrypt-dev locales python3 \
  python3-git python3-jinja2 python3-pexpect python3-pip \
  python3-subunit socat texinfo unzip wget xz-utils zstd
locale -a | grep -i en_US.utf8

Enable en_US.UTF-8 if the check fails. Build as a normal user, not with sudo bitbake.

2. Pin the 6.0.2 layers

Follow the official manual setup and pin all three repositories to the same release:

mkdir -p embedded-yocto/layers
cd embedded-yocto
git clone -b yocto-6.0.2 https://git.openembedded.org/bitbake layers/bitbake
git clone -b yocto-6.0.2 https://git.openembedded.org/openembedded-core layers/openembedded-core
git clone -b yocto-6.0.2 https://git.yoctoproject.org/meta-yocto layers/meta-yocto
source layers/openembedded-core/oe-init-build-env
printf '\nINIT_MANAGER = "systemd"\n' >> conf/local.conf
bitbake-getvar MACHINE
bitbake-getvar DISTRO
bitbake-getvar INIT_MANAGER
bitbake-layers show-layers

The script enters build/. Confirm MACHINE=qemux86-64. Yocto 6.0.2's nodistro defaults to systemd; the Poky reference distro can select a different init. This guide uses Poky, so it explicitly sets INIT_MANAGER = "systemd" in conf/local.conf and confirms it with bitbake-getvar INIT_MANAGER. Put the choice in your own distro configuration instead of relying on each developer's local file.

3. Build and boot the minimal image

bitbake core-image-minimal
ls -lh tmp/deploy/images/qemux86-64/
runqemu qemux86-64 core-image-minimal ext4 nographic

If ext4 was not generated, inspect bitbake-getvar IMAGE_FSTYPES and choose the actual type. The first build fetches and compiles many dependencies. Do not commit tmp/, downloads/, or sstate-cache/. In the guest:

uname -a
cat /proc/cmdline
cat /proc/1/comm
mount | grep ' on / '

Login policy depends on image configuration. Only on an isolated QEMU demo image, EXTRA_IMAGE_FEATURES = "empty-root-password" can allow an empty-password local console login. Never use it for networked or production images; do not enable empty-password SSH. Shut down with poweroff.

4. Add and start a systemd service

The repository's meta-demo layer contains a script, unit, recipe, and demo-image. From embedded-yocto/build/, check pwd then return to the source root:

cd ..
git clone --depth 1 https://github.com/yanruihe/yanruihe.github.io.git site
cp -a site/knowledge-base/examples/meta-demo layers/meta-demo
source layers/openembedded-core/oe-init-build-env
bitbake-layers add-layer ../layers/meta-demo
bitbake-layers show-recipes hello-yocto
bitbake demo-image
runqemu qemux86-64 demo-image ext4 nographic

In the guest:

cat /proc/1/comm
systemctl is-enabled hello-yocto.service
systemctl is-active hello-yocto.service
cat /run/hello-yocto/status
journalctl -u hello-yocto.service -b --no-pager

Expect enabled and active. Otherwise inspect init, package inclusion, unit installation, and logs. The example includes Dropbear for isolated development; remove unnecessary SSH and use a proper account/key policy before deployment. Its LICENSE = "CLOSED" is a demo placeholder.

5. Move to real hardware

Record repository commits, MACHINE, DISTRO, INIT_MANAGER, layer revisions, and images. Choose a 6.0.2-compatible BSP and validate bootloader, kernel configuration, device tree, partitions, serial console, networking, flashing, and rollback. Commit layers, recipes, and config, not edits to tmp/work/ or built images. For build errors inspect temp/log.do_*; for runtime errors inspect serial output, systemctl status, and journalctl.

6. Understand BitBake tasks and build directories

The argument to bitbake core-image-minimal is a recipe target, not a Linux kernel make target. BitBake parses visible layers and configuration, then calculates task dependencies. Package tasks commonly include do_fetch, do_unpack, do_patch, do_configure, do_compile, do_install, and do_package. Tasks may run in parallel and unchanged tasks can reuse sstate-cache; the first build is slow, while later changes often rebuild only affected tasks.

PathPurposeCommit to product Git?
conf/local.conf, conf/bblayers.confLocal target settings and enabled layersUsually not a personal build directory; move product defaults to a versioned layer/distro
tmp/work/Recipe workspaces, build output, task logsNo; BitBake can recreate it
tmp/deploy/images/<machine>/Kernel, bootloader, images, manifestsArchive as build artifacts, not source
downloads/Upstream source cacheShare/cache if useful; normally not Git source
sstate-cache/Reusable task outputCan live on team infrastructure; not product source
layers/Recipes, configuration, patches, metadataYes; pin each repository revision

Inspect final variable values with bitbake-getvar MACHINE or bitbake-getvar IMAGE_FSTYPES. Inspect merged settings with bitbake -e hello-yocto. Check visible layers, recipes, and tasks with:

bitbake-layers show-layers
bitbake-layers show-recipes hello-yocto
bitbake -c listtasks hello-yocto
bitbake -g demo-image

bitbake -g creates dependency graph files that explain why an image pulls in packages. After editing a recipe, build bitbake hello-yocto first, then bitbake demo-image. Do not delete all of tmp/ as the first response to an error; start with the failing task log and expanded variables.

7. Create a layer and recipe

The earlier meta-demo is a complete repository example. To start from scratch instead, create a separate meta-practice layer; do not enable both layers if they define recipes with the same names:

bitbake-layers create-layer ../layers/meta-practice
bitbake-layers add-layer ../layers/meta-practice
bitbake-layers show-layers

The repository example's service layer has this structure; use the same paths inside meta-practice if writing it yourself:

layers/meta-practice/
├── conf/layer.conf
├── recipes-demo/hello-yocto/hello-yocto_1.0.bb
├── recipes-demo/hello-yocto/files/hello-yocto.sh
├── recipes-demo/hello-yocto/files/hello-yocto.service
└── recipes-core/images/demo-image.bb

The recipe inherits systemd, declares local files, installs the script/unit, and sets SYSTEMD_SERVICE:${PN}. The image recipe adds the package with IMAGE_INSTALL:append. The service writes a status file under /run/hello-yocto/status; its unit uses Restart=on-failure, and QEMU verifies it with systemctl and journalctl. The complete files are in the meta-demo example directory. Replace the LICENSE = "CLOSED" placeholder with the real SPDX license and checksum information before product use.

Understand task cleanup first: -c clean removes a work directory, while -c cleansstate also drops that recipe's shared-state cache and slows other builds. Use the latter only with evidence and an accepted rebuild cost. Version product MACHINE, DISTRO, init, and application choices in a layer. Use bitbake-layers create-layers-setup or the team's manifest tool to record every layer repository and revision.

8. Common failures and where to look

SymptomCheck firstAction
do_fetch failsProxy, DNS, URL, Git ref, checksumConfirm source access; do not switch to an unpinned master branch
Nothing PROVIDESLayer inclusion, recipe name, show-recipesCheck bblayers and layer dependencies; distinguish recipe/package/image names
PID 1 is not systemdbitbake-getvar INIT_MANAGER, distro settingsFix init before building and verify the intended build directory/distro
Service does not startPackage inclusion, unit path, SYSTEMD_SERVICEInspect systemctl status and journalctl -u ... -b
QEMU cannot boot imageMACHINE, image type, runqemu argsCheck actual deploy files and IMAGE_FSTYPES
Recipe edit has no effectSelected layer/append, expanded values, task logUse bitbake-layers show-appends and bitbake -e hello-yocto

tmp/work/<arch>/<recipe>/<version>/temp/ usually contains log.do_* and run.do_*: the first is task output, the second its execution script. Start with the task BitBake reported as failed. If a running service behaves incorrectly, inspect its journal, permissions, runtime dependencies, and networking.

9. Team builds, releases, and choosing a build system

For each release, record BitBake, OpenEmbedded-Core, meta-yocto, BSP, and product layer revisions; MACHINE, DISTRO, INIT_MANAGER, image target, source mirror/hash-server settings, and artifact hashes. Review pinned SRCREV/checksums, patch provenance, licenses, runtime dependencies, and service privileges. local.conf is for local experiments; product defaults belong in versioned distro, machine, image, and layer configuration so clean CI can reproduce them.

Buildroot often fits compact configurations where one team produces a complete root filesystem image. Yocto often fits multiple boards and distro policies, shared layers across teams, and long-lived recipe and SDK maintenance. Also consider the silicon vendor's BSP, team experience, update plan, and support period. Neither system automatically provides secure OTA, signing-key management, or factory rollback.
