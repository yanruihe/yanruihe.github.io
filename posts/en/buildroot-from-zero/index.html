Embedded Linux from scratch: Buildroot
yanruiheBuildroot
2026-09-23 · Buildroot 2025.02.18 LTS · QEMU x86_64

Build a toolchain, Linux kernel, and root filesystem from source, then boot the result in QEMU. Virtual firmware handles early boot here; a real ARM board still needs its own bootloader, device tree, drivers, and BSP.

How it works · Host · Build · Boot · Configuration · Troubleshooting · Product

First, why can Buildroot build a whole system?

Buildroot does not reimplement Linux in C. It is primarily a framework of Makefiles, Kconfig configuration, scripts, and patches. The kernel, GCC, C library, and BusyBox are separate upstream projects. Buildroot selects versions and options, resolves package dependencies, fetches sources, cross-compiles components, installs them into a target filesystem, and produces the requested images. Thus make drives a configured build graph rather than one giant C program.

Board defconfig → .config → toolchain (binutils / GCC / C library, or external)
                         → target packages (BusyBox and applications)
                         → kernel / optional bootloader → root filesystem → images

This is a responsibility map, not a strict task execution order. The qemu_x86_64_defconfig in this article builds a kernel and root filesystem while QEMU provides virtual BIOS firmware; this example does not build U-Boot. The C library is configurable rather than always musl. BusyBox supplies small userspace utilities and the default init, not the kernel or Buildroot itself.

1. Prepare the host

Build on Linux as a normal user. On Windows, use a Linux VM or WSL2's Linux filesystem, not a Windows-mounted build directory. These commands target Ubuntu 24.04; consult the official host requirements elsewhere. Allow ample disk, RAM, and network capacity.

sudo apt update
sudo apt install -y build-essential git wget cpio unzip rsync file bc \
  bzip2 gzip xz-utils patch sed gawk qemu-system-x86

Use sudo only for host package installation, never for make.

2. Pin and build the image

git clone --branch 2025.02.18 --depth 1 https://gitlab.com/buildroot.org/buildroot.git buildroot
cd buildroot
git describe --tags --always
make qemu_x86_64_defconfig
make
ls -lh output/images/
test -s output/images/bzImage
test -s output/images/rootfs.ext2

The initial build fetches sources and creates the toolchain, packages, kernel, and filesystem. Do not assume a top-level make -j is needed. Keep the artifacts distinct:

PathPurpose
.configFull configuration; make savedefconfig extracts a smaller board configuration for version control
output/build/Per-component extraction, configuration, and compilation
output/host/Host tools, cross-toolchain, and target sysroot; output/staging/ is a compatibility symlink to that sysroot
output/target/Almost the target filesystem, but lacking proper device nodes and some permissions; do not deploy it
output/images/Kernel, root filesystem, and other final artifacts selected by the configuration

3. Boot QEMU and verify

Follow the selected defconfig's board readme:

qemu-system-x86_64 -M pc \
  -kernel output/images/bzImage \
  -drive file=output/images/rootfs.ext2,if=virtio,format=raw \
  -append 'rootwait root=/dev/vda console=tty1 console=ttyS0' \
  -serial stdio -net nic,model=virtio -net user

The login prompt appears in QEMU's graphical window. In the guest, inspect:

uname -a
cat /proc/cmdline
cat /proc/1/comm
mount | grep ' on / '

Confirm the kernel, root device, init, and root mount, then shut down with poweroff. Do not hand-edit rootfs.ext2 as persistent configuration.

4. Add a boot-time action

This minimal setup uses BusyBox init, not systemd. Run mkdir -p board/demo/overlay/etc/init.d and create board/demo/overlay/etc/init.d/S99demo:

#!/bin/sh
case "$1" in
  start) echo 'Buildroot demo is ready' >/dev/console ;;
  stop) ;;
  *) exit 1 ;;
esac

Run chmod +x board/demo/overlay/etc/init.d/S99demo and make menuconfig. Set System configuration → Root filesystem overlay directories to board/demo/overlay. Save, run make, and boot again. Look for the message and run test -x /etc/init.d/S99demo in the guest. Production applications should be Buildroot packages; the overlay is a minimal demo.

5. Preserve and port

make savedefconfig BR2_DEFCONFIG=board/demo/demo_defconfig
git status --short

Commit the defconfig, overlay, patches, and pinned versions, not the entire output/ tree. A config file alone does not guarantee a byte-for-byte reproducible build: pin Buildroot and external source versions, patches, toolchain, and host environment. For real hardware, select a matching board defconfig and verify CPU/ABI, bootloader, kernel configuration, device tree, partitions, serial console, and flashing procedure. A QEMU image is not directly flashable to an unrelated board. For build errors, inspect the failing package and output/build/; for boot errors, check kernel arguments, root device, and serial output. Buildroot does not automatically solve OTA, security updates, or product lifecycle management. Handle source and license obligations before shipping. For layered metadata and distribution policy, compare the Yocto from-zero guide.

6. Follow the build from configuration to image

The menu records which components the target product needs. make qemu_x86_64_defconfig writes maintained defaults to .config; make menuconfig changes them; the top-level Makefile schedules package tasks by dependency. The toolchain supplies a target compiler, linker, and C library. User-space programs use it, while the kernel and bootloader are built from their own upstream source trees.

If a selected network application depends on OpenSSL, Buildroot first prepares the target headers and libraries, then cross-compiles the application. A package .mk describes its source, configuration, build, and installation; Config.in controls its menu entry. The rootfs skeleton, packages, overlay, device table, and permissions make up user space; a filesystem generator packages them in the selected format. Buildroot is the Makefile-driven integrator, while the components remain independent projects.

StageMain inputsResult
Configurationdefconfig, menuconfig, board options.config, kernel and BusyBox configuration
ToolchainCPU/ABI, C library, compiler versionCross tools in output/host/bin/
System componentsKernel, optional bootloader, BusyBox, packagesFiles installed into staging/target
Image generationskeleton, overlay, device table, filesystem typeBoot/flash artifacts in output/images/

Buildroot can build an internal toolchain or use an external cross-toolchain; the C library is a target choice. QEMU virtual firmware loads the kernel for this demo. A real board also needs a matching bootloader, DDR and boot-media initialization, device tree, and vendor BSP. Decide which parts Buildroot owns and which the vendor supplies.

7. Change configuration in small steps

mkdir -p board/demo
cp .config board/demo/qemu_x86_64_base.config
make menuconfig
diff -u board/demo/qemu_x86_64_base.config .config
make
make savedefconfig BR2_DEFCONFIG=board/demo/demo_defconfig
diff -u configs/qemu_x86_64_defconfig board/demo/demo_defconfig

Common menus cover Target options (architecture/ABI), Toolchain (C library/compiler), System configuration (hostname, password policy, init and device management), Target packages, Kernel, and Filesystem images. Choose from the board and application requirements: every extra package adds image size, dependencies, and maintenance/security work.

Linux, BusyBox, and the C library each have their own configurator:

make linux-menuconfig
make busybox-menuconfig
make uclibc-menuconfig   # only when using uClibc-ng

Save a kernel configuration with make linux-update-defconfig; BusyBox has busybox-update-config. Available targets vary with the configuration, so consult make help and the pinned manual. Commit the compact defconfig, kernel/BusyBox configuration, patches, and overlay together. Do not commit only a workstation-specific .config or absolute paths. After changing a package, inspect dependencies and rebuild it:

make openssl-show-depends
make openssl-rebuild
make V=1

Replace the example package name with the actual target. V=1 prints full commands to inspect flags, include paths, and libraries. A configuration or dependency change may require the package's reconfigure/dirclean target before the top-level build refreshes dependents.

8. Add files, applications, and services

A rootfs overlay suits a small number of defaults, static files, or startup scripts. Its directory layout mirrors the target root: board/demo/overlay/etc/... becomes /etc/... in the guest. This guide's S99demo uses BusyBox init. Buildroot's init is configurable; when using systemd, provide systemd units and package integration instead of treating a BusyBox /etc/init.d/ script as a universal service definition.

An overlay is not a package manager. A production application should be a Buildroot package so its source version, dependencies, build flags, install paths, and license metadata can be reviewed and rebuilt. A custom package normally has Config.in and .mk files: the former defines its Kconfig option/dependencies, and the latter describes source retrieval, cross-compilation, and installation. Put them in a BR2_EXTERNAL tree and version that tree with the product defconfig instead of patching upstream Buildroot. For multiple distribution policies and broader metadata reuse, see the Yocto guide.

9. Separate build errors from boot errors

SymptomCheck firstNext step
Download failureoutput/build/<package>/, dl/, final errorCheck network/proxy, upstream URL, and checksum; distinguish fetch from compile errors
Missing header or libraryFailing package's config.log and dependenciesConfirm dependency selection and distinguish host/target packages
Host architecture in link commandCompiler command, output/host/bin/Target packages must use Buildroot's cross-toolchain
QEMU cannot find rootfsArguments, generated filename, /proc/cmdlineCheck virtio root device and generated image format
Kernel starts without login promptconsole=, getty, QEMU terminal/windowUse the board readme for the selected defconfig
Overlay file is absentOverlay path in .config, file permissionsSave the overlay setting and check executable mode

Build logs usually identify the failed package. Fix its dependency, toolchain setting, or patch, then rebuild affected packages; clean the full output only when you have confirmed it is corrupted. On a restricted network, run make source to fetch the sources selected by the configuration and move the download directory to the build host.

10. From QEMU demo to product

QEMU validates that a configuration boots. It does not validate a real board's DDR, boot media, GPIO, display, wireless, power management, or factory flashing. Obtain the vendor BSP and supported versions, then confirm the SoC/ABI, boot stages, kernel defconfig, device tree, root partition, partition table, console, and update/rollback plan. Boot a minimal image first, then add drivers and applications in batches while saving images and serial logs.

make legal-info

Review warnings, package manifests, and license texts in output/legal-info/README; this is supporting material, not a substitute for license review. Version the pinned Buildroot revision, defconfig, external tree, patches, board files, application revisions, and build instructions. A clean Linux CI host should rebuild and archive image hashes. Field updates need separate signature checks, A/B or recovery partitions, rollback, key management, and security-update policy.
