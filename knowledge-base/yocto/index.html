Yocto 使用知识库
yanruiheYocto
Yocto 6.0.2 / BitBake / Layer / Recipe / Image / devtool

以 Yocto Project 6.0.2（Wrynose）为目标版本，把硬件、软件包和发行版配置组织成可复现的系统镜像。

Poky、BSP 和其他层应使用兼容的 6.0.2 修订。动手实践可跳到systemd 服务 Demo和排错案例。

1. 核心概念

Yocto Project 不是一个固定发行版，而是一套用 OpenEmbedded 构建定制 Linux 系统的工具和元数据。

  • BitBake：解析元数据并执行任务。
  • Recipe（配方）：描述源码、依赖、编译、安装和打包方式。
  • Layer（层）：按功能隔离和组合配方、类、机器与发行版配置。
  • Machine：描述目标硬件平台；Image 描述最终系统镜像。
Layer → Recipe → Package → Image
  └──── Machine / Distro 配置影响解析与构建结果

2. 初始化与第一次构建

下面是通用流程，实际使用时必须让 poky、BSP 层和其他层处于相互兼容的 6.0.2 修订：

git clone https://git.yoctoproject.org/poky
cd poky
git checkout <matching-6.0.2-revision>
source oe-init-build-env build

bitbake-layers show-layers
bitbake core-image-minimal

构建前确认 MACHINE、DISTRO、下载目录和共享状态缓存配置。第一次构建通常需要较长时间，后续构建应尽量复用 DL_DIR 和 SSTATE_DIR。

3. 创建和接入自定义层

bitbake-layers create-layer ../meta-myproduct
bitbake-layers add-layer ../meta-myproduct
bitbake-layers show-layers

建议把产品定制放在独立层中，不直接修改 poky 或 meta-openembedded。常见结构如下：

meta-myproduct/
├── conf/layer.conf
├── recipes-apps/demo/demo_1.0.bb
├── recipes-core/images/myproduct-image.bb
└── recipes-kernel/linux/linux-%.bbappend

4. 配方与镜像

配方至少要明确源码、许可证、依赖和构建任务。对现有软件的定制优先使用 .bbappend，避免复制整份上游配方：

IMAGE_INSTALL:append = " demo"

变量覆盖语法与发行版版本有关；升级分支时要检查 override 语法、层兼容性和依赖变化。

5. devtool 开发闭环

开发应用或修改已有配方时，可用 devtool 缩短“修改—构建—部署—固化”循环：

devtool add https://example.com/project.git
devtool modify <recipe>
devtool build <recipe>
devtool deploy-target <recipe> root@<target-ip>

# 源码仓库提交后固化到正式层
devtool finish <recipe> ../meta-myproduct
devtool reset <recipe>

部署到目标机前先确认 SSH、目标架构和运行时依赖；devtool finish 前确认源码仓库已经提交。

6. 调试清单

# 查看最终变量值及其来源
bitbake -e <recipe> | less

# 查看任务依赖或执行单个任务
bitbake -g <recipe>
bitbake <recipe> -c compile

# 进入配方的开发 shell
bitbake <recipe> -c devshell

# 清理配方后重新构建
bitbake <recipe> -c cleansstate

# 查询已生成包的文件归属
oe-pkgdata-util find-path /usr/bin/<program>

遇到“找不到配方”先检查层是否加入、配方名是否正确；遇到“配置没有生效”先用 bitbake -e 确认变量来源；遇到增量构建异常再有针对性地清理任务。

7. 可复现与发布

  • 固定 manifest、层分支或 commit，而不是只记录模糊版本号。
  • 记录 MACHINE、镜像目标、构建时间、构建主机和关键配置。
  • 将自定义层、配方、补丁和 conf 配置放入 Git；不要提交 tmp/、downloads/、sstate-cache/ 等生成目录。
  • 发布前完成一次干净环境构建或 CI 验证，并保存镜像校验值。

8. 实际案例：把 systemd 服务加入镜像并开机启动

本案例包含 Layer、Recipe、脚本、unit 和 Image Recipe。完整文件可从meta-demo 示例层下载。从包含 poky 的目录进入 6.0.2 构建环境，先确认初始化系统：

source poky/oe-init-build-env build-demo
bitbake-getvar DISTRO
bitbake-getvar INIT_MANAGER
bitbake-getvar DISTRO_FEATURES

6.0.2 的 nodistro 默认使用 systemd，但 Poky 默认仍是 SysVinit；厂商发行版也可能有自己的设置。若 INIT_MANAGER 已是 systemd，无需重复配置。只有当前项目不是 systemd、而目标镜像确实要用 systemd 时，才在产品 distro 配置（演练时可在 conf/local.conf）明确写入 INIT_MANAGER = "systemd"，然后重新构建镜像。

meta-demo/
├── conf/layer.conf
├── recipes-demo/hello-yocto/hello-yocto_1.0.bb
├── recipes-demo/hello-yocto/files/hello-yocto.sh
├── recipes-demo/hello-yocto/files/hello-yocto.service
└── recipes-core/images/demo-image.bb

hello-yocto_1.0.bb 安装脚本和 unit，并声明自动启用服务；demo-image.bb 通过 IMAGE_INSTALL:append = " hello-yocto" 将包加入镜像。脚本每 10 秒更新 /run/hello-yocto/status。unit 的 ExecStart 指向安装后的脚本，WantedBy=multi-user.target 指定开机启用时所属的 target：

[Service]
Type=simple
ExecStart=/usr/bin/hello-yocto.sh
Restart=on-failure

[Install]
WantedBy=multi-user.target

Recipe 的关键配置如下：

SRC_URI = "file://hello-yocto.sh file://hello-yocto.service"
S = "${UNPACKDIR}"
inherit allarch systemd

do_install() {
    install -d ${D}${bindir} ${D}${systemd_system_unitdir}
    install -m 0755 ${UNPACKDIR}/hello-yocto.sh ${D}${bindir}/hello-yocto.sh
    install -m 0644 ${UNPACKDIR}/hello-yocto.service ${D}${systemd_system_unitdir}/hello-yocto.service
}
SYSTEMD_SERVICE:${PN} = "hello-yocto.service"
SYSTEMD_AUTO_ENABLE = "enable"

完整文件还应包含 SUMMARY、LICENSE 等元数据；正式项目使用真实许可证信息。将示例层复制到工作区后，在上述构建环境中执行：

bitbake-layers add-layer /path/to/meta-demo
bitbake-layers show-recipes hello-yocto
bitbake demo-image

/path/to/meta-demo 必须换成真实路径。构建成功后按机器和镜像格式选择 runqemu 参数，或启动目标板。

服务开机启动与手动启动

inherit systemd、SYSTEMD_SERVICE:${PN}、SYSTEMD_AUTO_ENABLE = "enable"、unit 的 [Install] 节和镜像中的 hello-yocto 包共同决定新镜像能否开机启动服务。6.0.2 的 systemd class 默认也会启用服务，这里显式写出 SYSTEMD_AUTO_ENABLE 便于阅读。进入目标系统后验证：

cat /proc/1/comm
systemctl is-enabled hello-yocto.service
systemctl is-active hello-yocto.service
cat /run/hello-yocto/status
journalctl -u hello-yocto.service -b --no-pager

is-enabled 应为 enabled，is-active 应为 active；状态文件中的时间应持续更新。若服务已安装但未运行，在目标机上执行：

systemctl start hello-yocto.service
systemctl status hello-yocto.service
# 仅在可写根文件系统的开发镜像上：开机自启并立即启动
systemctl enable --now hello-yocto.service

正式镜像应通过 Recipe 启用服务，而不是依赖运行时手工修改。正式项目还应核对许可证、非 root 运行要求和目标 BSP 的 init 配置；示例中的 LICENSE = "CLOSED" 仅供演示。

9. 排错案例：包已构建，但镜像中没有服务

按“层 → 配方 → 包 → 镜像 → 运行时”逐层排查：

bitbake-layers show-layers
bitbake-layers show-recipes hello-yocto
bitbake -e demo-image | grep '^IMAGE_INSTALL='
oe-pkgdata-util find-pkg hello-yocto

若 Recipe 存在但 IMAGE_INSTALL 不含 hello-yocto，检查 Image Recipe 和包名；若镜像里已有包但服务不启动，检查 INIT_MANAGER、unit 安装路径、SYSTEMD_SERVICE:${PN}、systemctl status 与 journalctl。不要一开始就删除整个 tmp/ 或共享缓存。
