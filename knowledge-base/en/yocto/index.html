Yocto 6.0.2 / BitBake / Layers / Recipes / Images / devtool

Target Yocto Project 6.0.2 (Wrynose) and organize hardware, packages, and distribution configuration into reproducible system images.

Poky, BSP, and other layers should use compatible 6.0.2 revisions. Start with the complete from-zero build, or jump to the systemd service demo and troubleshooting example.

1. Core concepts

Yocto Project is not a fixed distribution. It is a set of tools and metadata for building customized Linux systems with OpenEmbedded.

  • BitBake: parses metadata and executes tasks.
  • Recipe: describes source, dependencies, compilation, installation, and packaging.
  • Layer: isolates and composes recipes, classes, machine, and distribution configuration.
  • Machine: describes the target hardware; an Image describes the final system image.
Layer → Recipe → Package → Image
  └──── Machine / Distro configuration affects parsing and build results

2. Initialize and build

This is a generic flow. The poky, BSP, and other layers must use compatible 6.0.2 revisions:

git clone https://git.yoctoproject.org/poky
cd poky
git checkout <matching-6.0.2-revision>
source oe-init-build-env build

bitbake-layers show-layers
bitbake core-image-minimal

Confirm MACHINE, DISTRO, download directories, and shared-state cache settings. Reuse DL_DIR and SSTATE_DIR where possible.

3. Create and add a custom layer

bitbake-layers create-layer ../meta-myproduct
bitbake-layers add-layer ../meta-myproduct
bitbake-layers show-layers

Keep product customizations in a separate layer instead of modifying poky or meta-openembedded directly. A common layout is:

meta-myproduct/
├── conf/layer.conf
├── recipes-apps/demo/demo_1.0.bb
├── recipes-core/images/myproduct-image.bb
└── recipes-kernel/linux/linux-%.bbappend

4. Recipes and images

A recipe should make its source, license, dependencies, and build tasks clear. Prefer a .bbappend to customize existing software instead of copying the entire upstream recipe:

IMAGE_INSTALL:append = " demo"

Override syntax depends on the release. Check syntax, layer compatibility, and dependencies when moving to a new branch.

5. The devtool loop

Use devtool to shorten the edit-build-deploy-finish loop:

devtool add https://example.com/project.git
devtool modify <recipe>
devtool build <recipe>
devtool deploy-target <recipe> root@<target-ip>

# Commit the source first, then finish it into the permanent layer
devtool finish <recipe> ../meta-myproduct
devtool reset <recipe>

Confirm SSH, target architecture, and runtime dependencies before deployment. Make sure the source repository is committed before devtool finish.

6. Debug checklist

# Inspect final variable values and their origins
bitbake -e <recipe> | less

# Inspect task dependencies or run one task
bitbake -g <recipe>
bitbake <recipe> -c compile

# Open a development shell
bitbake <recipe> -c devshell

# Clean a recipe and rebuild it
bitbake <recipe> -c cleansstate

# Find which package owns a file
oe-pkgdata-util find-path /usr/bin/<program>

For a missing recipe, check layers and the recipe name. For configuration that is not taking effect, inspect its origin with bitbake -e. For incremental build problems, clean only the affected task or recipe first.

7. Reproducibility and release

  • Pin a manifest, layer branch, or commit instead of recording only a vague version.
  • Record MACHINE, image target, build time, build host, and important configuration.
  • Put custom layers, recipes, patches, and conf configuration in Git; do not commit tmp/, downloads/, or sstate-cache/.
  • Run a clean build or CI verification before release and preserve the image checksum.

8. Practical example: add and start a systemd service

This example provides a complete layer with a recipe, script, service unit, and image recipe. Download the files from the meta-demo layer. From a directory containing poky, enter the 6.0.2 build environment and check the init system:

source poky/oe-init-build-env build-demo
bitbake-getvar DISTRO
bitbake-getvar INIT_MANAGER
bitbake-getvar DISTRO_FEATURES

In 6.0.2, nodistro defaults to systemd, but Poky still defaults to SysVinit; a vendor distribution may choose differently. If INIT_MANAGER is already systemd, do not set it again. Only when the current build is not using systemd and the target image requires it, set INIT_MANAGER = "systemd" in the product distro configuration (or conf/local.conf for a demo) and rebuild the image.

meta-demo/
├── conf/layer.conf
├── recipes-demo/hello-yocto/hello-yocto_1.0.bb
├── recipes-demo/hello-yocto/files/hello-yocto.sh
├── recipes-demo/hello-yocto/files/hello-yocto.service
└── recipes-core/images/demo-image.bb

The recipe installs the script and unit and enables the service. The image recipe adds the package with IMAGE_INSTALL:append = " hello-yocto". The script updates /run/hello-yocto/status every ten seconds. The unit's ExecStart points to the installed script, and WantedBy=multi-user.target identifies the boot target when enabled:

[Service]
Type=simple
ExecStart=/usr/bin/hello-yocto.sh
Restart=on-failure

[Install]
WantedBy=multi-user.target

Key lines from the recipe are below:

SRC_URI = "file://hello-yocto.sh file://hello-yocto.service"
S = "${UNPACKDIR}"
inherit allarch systemd

do_install() {
    install -d ${D}${bindir} ${D}${systemd_system_unitdir}
    install -m 0755 ${UNPACKDIR}/hello-yocto.sh ${D}${bindir}/hello-yocto.sh
    install -m 0644 ${UNPACKDIR}/hello-yocto.service ${D}${systemd_system_unitdir}/hello-yocto.service
}
SYSTEMD_SERVICE:${PN} = "hello-yocto.service"
SYSTEMD_AUTO_ENABLE = "enable"

The full file also needs metadata such as SUMMARY and LICENSE; use real license information in production. Copy the example layer into your workspace, then run in the build environment above:

bitbake-layers add-layer /path/to/meta-demo
bitbake-layers show-recipes hello-yocto
bitbake demo-image

Replace /path/to/meta-demo with the actual path. Choose runqemu arguments for your machine and image format, or boot the target board.

Start the service at boot or manually

inherit systemd, SYSTEMD_SERVICE:${PN}, SYSTEMD_AUTO_ENABLE = "enable", the unit's [Install] section, and the hello-yocto package in the image together make the service start on a fresh image. In 6.0.2 the systemd class enables services by default; the explicit SYSTEMD_AUTO_ENABLE makes that choice visible. On the target:

cat /proc/1/comm
systemctl is-enabled hello-yocto.service
systemctl is-active hello-yocto.service
cat /run/hello-yocto/status
journalctl -u hello-yocto.service -b --no-pager

is-enabled should return enabled, is-active should return active, and the timestamp in the status file should keep changing. If the unit is installed but not running, run on the target:

systemctl start hello-yocto.service
systemctl status hello-yocto.service
# Only on a development image with a writable root filesystem:
systemctl enable --now hello-yocto.service

Production images should enable the service in the recipe rather than rely on a runtime change. Check the real license, non-root execution, and the BSP's init configuration; LICENSE = "CLOSED" in this example is for a demo only.

9. Troubleshooting example: package built, service absent from image

Check each link in the chain: layer → recipe → package → image → runtime.

bitbake-layers show-layers
bitbake-layers show-recipes hello-yocto
bitbake -e demo-image | grep '^IMAGE_INSTALL='
oe-pkgdata-util find-pkg hello-yocto

If the recipe exists but IMAGE_INSTALL omits the package, check the image recipe and package name. If the package is present but the service does not start, inspect INIT_MANAGER, unit installation path, SYSTEMD_SERVICE:${PN}, systemctl status, and journalctl. Do not start by deleting all of tmp/ or the shared cache.
