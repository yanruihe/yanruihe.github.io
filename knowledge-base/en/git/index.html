Reusable workflows for branches, commits, synchronization, and recovery

Confirm the state before changing it; make the change recoverable before cleaning anything up.

This page covers Git workflows, branch management, commit reviews, and version recovery.

1. Mental model

Git work is easiest to reason about as four areas: working tree, staging area, local repository, and remote repository.

Working tree --git add--> Staging area --git commit--> Local repo --git push--> Remote repo
   ^                                      |
   +------------- git restore ------------+

Start with git status, then decide whether to stage, commit, undo, or synchronize.

2. Daily workflow

git switch main
git pull --ff-only origin main
git switch -c feature/short-description

git status
git diff
git diff --check
git add -p
git commit -m "docs: update git notes"

git fetch origin
git rebase origin/main
git push -u origin HEAD

Small commits are easier to review and revert. Use prefixes such as docs:, feat:, fix:, and build:; describe the result rather than only the action.

3. Branching, merging, and rebasing

  • Use short-lived branches for features or knowledge topics, such as feature/logging.
  • Rebase local, unpublished commits when you need to tidy the history.
  • Do not rewrite commits that others already depend on; add a corrective commit instead.
  • Before merging, make sure the worktree is clean and read the complete diff.
git log --oneline --decorate --graph -20
git diff origin/main...HEAD
git diff --name-only origin/main...HEAD

4. Safe undo and recovery

# Cancel an uncommitted working-tree change
git restore -- path/to/file

# Unstage a file while keeping the working-tree change
git restore --staged -- path/to/file

# Revert a published commit with a new inverse commit
git revert <commit>

# Find lost commits or branch pointers
git reflog

reset --hard discards working-tree content. For shared branches, prefer revert when correcting history.

5. Commit and review conventions

  • Keep each commit focused on one logical change so it is easy to understand, review, and revert.
  • Use a short prefix for the type and scope, for example docs(git): clarify restore examples.
  • Review the complete diff and check for secrets, temporary files, or unrelated changes before committing.
  • Record review feedback and verification results before merging; add a clear follow-up commit when changes are needed.

6. Publish to a remote repository

git fetch origin
git switch main
git pull --ff-only origin main
git switch -c docs/update-git-notes
# Edit Git documentation or related files
git diff --check
git add path/to/changed-files
git commit -m "docs(git): update workflow notes"
git push -u origin HEAD
